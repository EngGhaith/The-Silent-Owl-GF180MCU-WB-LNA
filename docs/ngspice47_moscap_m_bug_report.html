GF180MCU · ngspice-47 simulator bug

ngspice-47 fails to load GF180MCU I/O pad netlists — unknown parameter (e9)

Every branch of the Silent Owl LNA (main, dev_ghaith, dev_ilir) instantiates the same GF180MCU RF pad cell. Its vendor SPICE model triggers a netlist-parser bug in ngspice-47 that aborts simulation before any analysis runs — independent of the LNA circuit itself.

Scope all 3 branches Stage circuit load (pre-analysis) Status workaround applied, upstream fix needed

Summary

ngspice-47 cannot load any GF180MCU netlist that instantiates the gf180mcu_fd_io__asig_* I/O pad cells, because the pad's vendor model uses an X-instance multiplier (m=) on a subcircuit containing a nonlinear (voltage-dependent) behavioral capacitor (C … C='<expr>'). Combining m= with that kind of capacitor corrupts an internally auto-generated element line, and the simulator aborts before any analysis runs.

The PDK's own versions.txt pins ngspice 43 as the intended simulator; only ngspice-47 is installed here. This looks like a regression between those releases — not confirmed against 43 directly, since no 43 binary was available to test.

Symptom

Netlisting xschem/lna-core_tb.sch (any branch) and running the result through ngspice -b fails immediately at circuit-load time, before any .control statement executes:

ngspice -b lna-core_tb.spiceaborted
Error on line 1412 or its substitute:
  g.x2.x1.gc_moscap x2.x1.c_moscap_int1 0 0 vddio   3.600000000000000e+01    e9
  unknown parameter (e9)
    Simulation interrupted due to error!

Error: incomplete or empty netlist
       or no ".plot", ".print", or ".fourier" lines in batch mode;
no simulations run!

x2 is the gf180mcu_fd_io__asig_5p0 RF pad instance; .x1 and c_moscap are internal to the pad's vendor subcircuit — nothing in the LNA design is involved. g.x2.x1.gc_moscap and x2.x1.c_moscap_int1 are ngspice's own auto-generated helper names for the nonlinear capacitor, created when it expands a C=<expr> line into charge-storage form — they appear in no source file.

Minimal reproduction

Fully independent of the LNA circuit — reproduces with a 2-line netlist against the stock PDK files:

repro.spice8 lines
.title moscap_m_bug
.include /foss/pdks/gf180mcuD/libs.tech/ngspice/design.ngspice
.lib     /foss/pdks/gf180mcuD/libs.tech/ngspice/sm141064.ngspice typical
.lib     /foss/pdks/gf180mcuD/libs.tech/ngspice/sm141064.ngspice moscap_typical

X1 vdd 0 cap_nmos_06v0 m=1.0 c_length=15e-6 c_width=15e-6
V1 vdd 0 3.3
.control
op
.endc
.end

Result: same unknown parameter (e9) error. Isolating further:

  • Removing m= entirely (any value, including the implicit default m=1) → works.
  • Keeping m= but swapping in a linear capacitor (plain numeric C=, no voltage dependence) → works.
  • Keeping the nonlinear cap and m= together, at any multiplier — tested 1.0, 2.0, 4.0, 36.0, 36 — → fails identically every time.

So the trigger is specifically m= on an X-instance of a subcircuit containing a C ... C='<expr>' capacitor — independent of the multiplier's magnitude.

sm141064.ngspice · cap_nmos_06v0vendor model
.subckt cap_nmos_06v0 1 2 c_length=l c_width=w dtemp=0
.param cvar1=0.001107
.param cvar2=0.00107
.param cvar3=6.25
.param cvar4=-4.1875
c_moscap 1 2 c='cap_nmos_06v0_corner*c_length*c_width*(cvar1+cvar2*tanh(cvar3*v(1,2)+cvar4))' dtemp=dtemp
.ends cap_nmos_06v0

The I/O pad file instantiates it 18 times, always as X<n> <net1> <net2> cap_nmos_06v0 m=<M> c_length=<L> c_width=<W> — ESD/decoupling MOS-caps, m ranging 4–70 across the 18 sites.

Impact

Any GF180MCU design instantiating gf180mcu_fd_io__asig_* — or presumably any pad relying on cap_nmos_06v0 / cap_pmos_06v0 / cap_nmos_03v3 / cap_pmos_03v3 with an m= multiplier — cannot be netlisted-and-run at all under this ngspice-47 build. The failure is at circuit load, before any analysis, so it blocks every simulation type equally: .op, .ac, sp, .noise, transient.

Workaround applied

cap_nmos_06v0's capacitance is exactly linear in c_width — the tanh(...) term depends only on terminal voltage, never on width — so folding the multiplier into the width is an algebraic identity, not an approximation:

m = M,  c_width = W  ≡  (no m),  c_width = M×W

A local patched copy of just the I/O pad file was made — the shared /foss/pdks install was left untouched — rewriting all 18 m=-bearing instances this way:

gf180mcu_fd_io.spice · local patch1 of 18 sites
- X1 DVDD DVSS cap_nmos_06v0 m=36.0 c_length=15e-6 c_width=15e-6
+ X1 DVDD DVSS cap_nmos_06v0 c_length=15e-6 c_width=0.00054

Each generated testbench netlist's .include for the pad file was redirected to this patched copy before invoking ngspice -b. All three branches then netlist and simulate to completion.

Recommendation

  • Treat this as an ngspice-47 regression, not a PDK or design bug — file it upstream against ngspice (netlist parser / nonlinear-capacitor expansion), referencing the 8-line repro above.
  • Until fixed: either pin the PDK-recommended ngspice 43 for this flow, or apply the m=→c_width folding workaround to any locally used copy of the affected library file — never edit the shared /foss/pdks install in place.
  • Worth checking whether other GF180MCU pad/cell files beyond gf180mcu_fd_io.spice use the same m= + nonlinear-cap pattern — they would hit the identical failure.
