cgdegLloadL_cscascloadL_noBuf — generic pad vs. 0 Ω PEX pad

CG (no cascode, inductive source degeneration, inductive drain peaking) → CS+cascode (inductive drain peaking), passive output match, no buffer. Centered at 2.4 GHz. Two branches of the same core circuit, differing only in which I/O ESD pad model terminates the RF ports.

Starting point was the archived dev_ilir_inductive_degen branch (commit 05107ff). Its as-inherited matching (LIN=7n/RLIN=14Ω/C11=0.8p) measured only −2.5 to −3.8 dB S11/S22 against the generic pad — good gain-bandwidth, poor return loss. cgdegLloadL_cscascloadL_noBuf below is a full retune of every R/L/C and bias in the circuit, targeting <−10 dB S11/S22 without giving up the gain-bandwidth. cgdegLloadL_cscascloadL_noBuf_pex reuses that exact circuit unchanged and retunes only the pad-facing matching elements (LIN/RLIN, C11) for the real extracted pad's different impedance.

Design optimization methodology

Both retunes used the same approach: build the testbench with each candidate's component values substituted in, run a narrow 21-point 2.3–2.5 GHz S-parameter sweep (full broadband/stability runs are reserved for the final candidate only), and score the result. The cost function penalizes S11/S22 worse than −10 dB, rewards S21, and lightly penalizes NF:

cost = mean(relu(S11+10)) + mean(relu(S22+10)) - 0.08*mean(S21) + 0.04*mean(NF)

For any bias sweep, candidates are also rejected unless every device's DC operating point stays in healthy strong-inversion saturation (VOV > 80 mV, VDS−VDSAT > 150 mV for XM1/XM2/XM4) — an earlier pass found a "good S11" region that turned out to be pushing the CG device (XM2) into subthreshold (VOV < 0), which is excluded.

Generic-pad branch: full R/L/C/bias retune

Free parameters: LIN (with RLIN = ωL⁄Q, Q=12 fixed, so RLIN is never tuned independently of LIN), LDEG, LD4, RLD3, LD2, RLD2, C11, VBIAS_CG, VBIAS_CS, VBIAS_CAS — 9 free dimensions. ~24,000 evaluations across a global random search followed by two rounds of local refinement (tightening bounds around the best cluster each round) converged on a stable optimum with worst-case in-band S11 ≈ −9.4 dB, S22 consistently below −9 dB (often far below), S21 up ~7 dB versus the inherited design, and NF down ~2 dB. The tradeoff: the converged bias point draws roughly 1.75× the inherited design's current (higher VBIAS_CG and VBIAS_CS push more current through XM1/XM2/XM4 for the extra gm the match needed).

PEX branch: matching-only retune

Free parameters: LIN (RLIN = ωL⁄Q, Q=12) and C11 only — everything else (device sizes, LDEG, LD4/RLD3, LD2/RLD2, biases) carried over unchanged from the generic-pad branch's retuned circuit. A coarse 10×10 grid followed by a finer 7×7 local grid (149 evaluations total against the real, much slower PEX netlist) converged on LIN=4.2 nH (RLIN=5.28 Ω), C11=1.93 pF.

Pad-model issues found and fixed

Both testbenches instantiate gf180mcu_fd_io__asig_5p0 exactly as the symbol netlists it (port order ASIG5V DVDD DVSS VDD VSS, from the symbol's own pinnumber attributes). Three independent, unrelated problems were found and fixed while wiring the real pad models up to this testbench:

1. Raw PDK pad model crashes ngspice-47 (generic-pad branch)

.include /foss/pdks/gf180mcuD/libs.ref/gf180mcu_fd_io/spice/gf180mcu_fd_io.spice — i.e. the pad model literally referenced in the inherited testbench, unmodified — deterministically aborts netlist load in this ngspice build: 
Error on line 1412 or its substitute:
  g.x2.x1.gc_moscap x2.x1.c_moscap_int1 0 0 vddio   3.600000000000000e+01    e9
  unknown parameter (e9)
Reproduced with a minimal 5-line standalone reinstantiation of just the asig_5p0 subcircuit, independent of everything else in the testbench. Root cause: the PDK cell instantiates its ESD MOS capacitor with a device multiplicity (m=36); elaborating that with this ngspice build corrupts an internal line while expanding the cap_nmos_06v0 compact model. This is the same cap_nmos_06v0 "m=" elaboration bug already worked around elsewhere in this project by expanding the multiplicity into individual unit-size instances instead of using "m=". Fix: xschem/gf180mcu_fd_io__asig_5p0_generic_pinfixed.spice (co-located with the testbench) reuses the project's own capacitance-extracted pad model (analog_pad_sp_paramerters/spice_files/extracted_gf180mcu_fd_io__asig_5p0_manually_scaled.spice, which already instantiates 36 individual unit MOS caps instead of one with m=36), with its .SUBCKT pin order corrected to match the symbol.

2. 0 Ω PEX extraction never ties its ASIG5V port into its own RC mesh

Every other port of the flat extraction (DVDD, DVSS, VDD, VSS) has an explicit element tying the bare port name into its parasitic mesh (e.g. R30992 DVDD.n5553 DVDD 0.456503). ASIG5V has none — every reference to it inside the extraction is a suffixed sub-node (ASIG5V.n9972, ASIG5V.t0, ...), never the bare port name, so the RF signal pin was only coincidentally connected. Fix: a single tie resistor was added at the end of the subcircuit, bridging the port to a well-connected hub node of its own mesh: 
R_ASIG5V_PIN_TIE ASIG5V ASIG5V.n9972 0.01

3. Pin-order mismatch in the PEX pad's own .SUBCKT declaration

The 0Ω PEX file's .SUBCKT line read gf180mcu_fd_io__asig_5p0 DVDD ASIG5V DVSS VDD VSS — the first two pins swapped relative to the symbol. Internal nodes are name-based, so only the port names on the .SUBCKT line needed to change, to ASIG5V DVDD DVSS VDD VSS.

Both fixed pad models live next to their testbench (xschem/gf180mcu_fd_io__asig_5p0_generic_pinfixed.spice and xschem/gf180mcu_fd_io__asig_5p0_pex__pdk_gf180mcuD__rcx__flat__cthresh_0__extresist_0mohm.spice respectively) and are referenced via $::env(PWD)/<filename> in the testbench's MODELS block, so the include resolves next to whichever checkout/worktree the branch lives in, rather than to a hardcoded absolute path.

Reproducing these results

Each branch's testbench (xschem/lna-core_tb.sch) is self-contained: run it directly from its own xschem/ directory (so the $::env(PWD) pad-model include resolves) and it reproduces the S-parameter, noise-figure and stability numbers above. The PEX branch's full 7000-point broadband sweep is slow (the flat PEX extraction is a ~3.7 MB, ~100,000-element netlist) — budget real time for it. The control script was also trimmed of a large block of dead op-point/noise-cancellation code inherited from a different (parallel CG/CS noise-cancelling) architecture that doesn't exist in this circuit — see the testbench's own comments for what was removed and why.
